01 / 결정

프레임워크 — Tauri v2가 아니라 Electron

관점 Tauri v2 Electron
렌더링 엔진 OS WebView → macOS는 WebKit, 플랫폼별 차이 실재 번들된 Chromium → 모든 OS에서 렌더링 일관
팀 스택 정합 네이티브 계층은 Rust (러닝코스트) TS/React/Next 그대로 — Rust 세금 없음
번들·메모리 ✓ 가볍다 무겁다 (Chromium 동봉)
성숙한 웹 제품 확장 그린필드엔 매력적 배포·서명·자동업데이트 생태계 성숙 → 리스크 낮음
결정 근거 새 그린필드라면 Tauri v2(2.0 stable, 2024.10)도 충분히 후보. 다만 성숙한 웹 제품 확장 초기엔 렌더링 일관성·스택 정합·배포 성숙도 때문에 Electron이 리스크 낮음. 번들·모바일이 중요해지면 재검토.
02 / 결정

웹 로딩 — 원격 URL(loadURL) 셸

기준 로컬 번들 · loadFile 원격 URL · loadURL
렌더링 모델 Next.js output:'export' (SSG) 만 가능 배포된 웹을 그대로 → SSR·미들웨어 살아있음
SSR / API / 미들웨어 ✕ 서버 기능 사용 불가 ✓ 기존 웹과 동일하게 동작
배포 웹 배포 + 앱 재빌드·재배포 이중 관리 웹 배포 1회 → 데스크톱도 자동 최신화
오프라인 ✓ 번들이 로컬에 있어 강함 △ 흰 화면 위험 — 기존 SW 캐싱으로 완화
적합성 제품을 export 제약 안으로 욱여넣어야 함 이미 PWA 서비스 + 배포 인프라 존재 → 자연스러움
결정 근거 이미 웹을 PWA로 배포·서비스 중이면 셸은 그 배포 주소를 띄우는 크롬리스 창이면 끝 — 웹 1회 배포로 데스크톱 자동 최신화 (슬랙·디스코드 데스크톱과 같은 계열). 트레이드오프인 오프라인 폴백·preload API 정합성은 인지만 하고 미구현(향후 과제).
03 / 결정

알림 — 전송은 WebSocket(강제), 표시는 메인 네이티브(선택)

표준 Web Push(SW + PushManager)는 Electron에 Push Service가 없어 경로 자체가 막힘 → 전송 수단은 사실상 결정됨.

경로 성격 판정
WebSocket + IPC 렌더러가 WS 수신 → IPC로 메인 → 네이티브 알림. 표준 의존성만 사용. 트레이 상주 시만 알림 = 슬랙·디스코드와 동일한 의도. 선택
표준 Web Push (SW+FCM) Electron에 Push Service 부재 → 경로 자체가 막힘. 불가
electron-push-receiver Node가 FCM·MCS 직접 구현. 비공식 리버스 프로토콜, 2024.6 이후 불안정 → 프로덕션 리스크 과다. 배제
OS 네이티브 푸시 (WNS·APNs) "앱 꺼져도 알림"의 정석. 지금 단계엔 과함. 향후
단계 선택 근거
전송 WebSocket 강제 Electron에서 표준 Web Push(FCM) 경로가 막힘 → 메시지를 받아올 방법이 상시 WS뿐. 선택이 아니라 결정됨.
표시 IPC → 메인 네이티브 선택 렌더러 웹 Notification으로도 뜨지만, 트레이에 숨긴 창 복원은 메인만 가능하고 창 제어·앱 정체성(setAppUserModelId)·클릭 라우팅이 이미 메인에 모여 있음 → 알림도 메인 네이티브로 일원화.
04 / 아키텍처

프로토타입 아키텍처와 실제 동작

직접 구현 · 동작 확인됨 설계·인지만 함 (미구현)

직접 구현하고 시연으로 확인한 것 확인됨

  • 최소화·트레이 상태에서도 WS 유지 → 네이티브 알림 (backgroundThrottling:false로 백그라운드 freeze 방지)
  • 미확인 개수 → 트레이 아이콘·독 배지·창 제목에 반영 (OS 통합; 개수를 어떻게 세는지는 앱 몫)
  • 알림 클릭 → 창 복원 + 대상 화면으로 라우팅 (open-room IPC)
  • 완전 종료 → 알림 없음 (슬랙·디코와 동일한 의도, isQuitting 플래그로 hide와 구분)
  • WS 끊김 → 1.5초 자동 재연결 · 두 번째 실행 시 새 창 대신 기존 창 포커스(단일 인스턴스 락)

인지했지만 이 데모에선 구현하지 않은 것 설계

  • catch-up 재동기화 — 재연결은 되지만 놓친 메시지 리플레이는 없음(데모 서버가 메시지를 영속화하지 않음).
  • presence(온라인·자리비움 같은 접속 상태) 크래시 보정 — client-reported 방식이라 크래시·단절 시 "항상 활성"으로 오인 가능. 프로덕션에선 서버 heartbeat/timeout 병행 필요.
  • 세션·오프라인 실제 배선 — 해법은 정리됨(persistent 쿠키 / SW 캐싱 + did-fail-load 폴백), 데모는 로컬 무인증 환경이라 미적용.
  • 패키징·코드 서명·자동 업데이트 — 개발 실행 기준, 배포는 범위에서 의도적으로 제외.
05 / 열린 질문

실제 구조를 확인하면 정해질 것들

  • 실시간 경로 — 실제 서버의 실시간 전송이 무엇인가 (WS / SSE / socket.io 등)? 데스크톱 알림을 이 상시 연결에 얹는 방식이 그대로 맞는지 확인 필요.
  • 배포 파이프라인 — 기존 웹 CI/CD에 데스크톱 빌드·서명·자동 업데이트를 어떻게 얹는가?
  • presence·읽음 처리 — 서버가 이미 presence/unread를 관리하는가? 데스크톱이 추가되면 동시 접속 기기가 늘어 클라이언트 각자 판단으로는 부족 → unread 동기화·알림 게이팅을 서버로 옮기는 게 자연스러운가?
